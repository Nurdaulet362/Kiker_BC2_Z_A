## 1. H0b — две правки перед основной работой (≈30 мин)

Ветка: `hackathon/h0b`. Обе правки в существующих файлах, без новых зависимостей.

### H0b-1. Резервная копия не должна затираться

Файлы: `src/session-storage.ts` (функция `flushKey`), `src/learning/storage-backup.ts`, тесты `tests/storage-backup.test.ts`, `tests/session-storage.test.ts`.

Проблема: один слот `<key>.backup` перезаписывается при любом закрытии черновика, поэтому копия с реально потерянными данными может быть заменена чистым состоянием.

Сделать: уточнить критерий потери данных и добавить два слота.
- Отбрасывание невалидных записей, потеря результатов или неподтверждённое исчезновение/вытеснение черновика требуют копии. Штатное закрытие черновика, подтверждённое `closedAttempts` в итоговом состоянии, не считается аварийной потерей и не трогает резервные слоты.
- `<key>.backup` — последняя копия с потерей данных.
- `<key>.backup.prev` — предыдущая.
- Перед записью нового `<key>.backup` текущее значение `<key>.backup` (если есть и отличается от нового исходника) копируется в `<key>.backup.prev`. Если исходник уже равен `.backup`, повторный flush не вращает слоты и не записывает их заново.
- Если запись любого из слотов падает, основной ключ не меняется (как сейчас).

Приёмка:
- Тест: два последовательных flush с потерей данных → оба исходных значения присутствуют (`.backup` и `.backup.prev`).
- Тест: flush без потери данных не трогает ни один слот.
- Тест: после сохранения повреждённого исходника минимум два штатных завершения черновиков не заменяют полезную копию.
- Отдельные тесты: ошибка записи `.backup.prev` и ошибка записи `.backup` оставляют основной ключ прежним.
- Тест: резервная копия записана, запись основного ключа упала; повторный flush сохраняет предыдущую отличающуюся копию, а не заполняет оба слота одинаковыми байтами.

### H0b-2. Клонирование payload до старта воркера

Файл: `src/worker-pool.ts`, метод `request()`.

Проблема: сейчас сначала вызывается `start()`, потом `structuredClone(payload)`. Ошибка клонирования вызывает `stop()` и убивает воркер для всех запросов.

Сделать: клонировать payload **до** `start()`. Если клонирование падает, отклонить только этот запрос `FormulaWorkerError("start")` и **не** вызывать `stop()`.

Приёмка:
- Тест (fake Worker): payload с функцией → этот запрос отклонён; следующий запрос успешен; `factory` вызван ровно один раз.
- Тест: корректный запрос уже ожидает ответа → неклонируемый payload отклоняется → исходный корректный запрос успешно завершается; `terminate` не вызван, `factory` остаётся равным 1. Ошибка клонирования обрабатывается отдельным catch без `stop()`.
- Существующие тесты `tests/worker-pool.test.ts` и `tests/workers.test.ts` зелёные.

Коммит: `fix(h0b): two backup slots; clone payload before worker start`.

Контракт варианта (сохранять в черновике и целиком в результате; использовать также при сбросе данных и восстановлении):
```
{ variantId, seed, generatorVersion, rows, transferQuestion, transferCorrect }
```
- `variantId` и `attempt` — разные поля. Бесплатный повтор: новый `attempt`, но `variantId` базового урока.

## 8. H6b — Stripe в тестовом режиме (раунд C, только если время позволяет)

Условие старта: владелец подтвердил тестовый аккаунт Stripe и переменные окружения (раздел 11).

Серверная часть (Vercel Functions, `api/`):
- `POST /api/checkout`: создаёт Checkout Session `mode: "subscription"` с `STRIPE_PRICE_ID` из env.
- `GET /api/session?session_id=`: получает Session с сервера Stripe и проверяет **все**:
  - `livemode === false` (тестовый режим);
  - `mode === "subscription"`;
  - `payment_status === "paid"`;
  - Price ID совпадает с ожидаемым.
  Статус `complete` сам по себе не означает оплату.
- Выдаёт подписанный HMAC-токен с `exp`. Срок действия токена не равен сроку подписки: при проверке учитывать текущий статус подписки.
- Отмена: Stripe Customer Portal (нужен для обещания «cancel anytime»). Без него обещание не публиковать.

Тесты: unpaid Session; expired Session; неверный Price ID; просроченный токен; поддельный токен; отмена продления с доступом до конца оплаченного периода.

Локальный запуск:
- `npm run dev` — автономный демо-checkout без серверных endpoint.
- `vercel dev` — API-режим для Stripe.

Приёмка (сквозная, до конца): оплата в test mode → возврат → доступ к Pro → перезагрузка сохраняет доступ. Редиректа на checkout.stripe.com недостаточно.

Если не закрыт весь путь к контрольной точке — остаётся демо-вход с меткой. Не показывать вид реального списания.
